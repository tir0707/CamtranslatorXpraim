# Архитектура

Windows-процесс владеет локальным HTTPS/WSS сервером, сертификатом и одноразовым кодом. Он публикует `_camxp._tcp` через DNS-SD. iPhone находит компьютер или получает его IP вручную. Это сознательное изменение направления discovery относительно исходного ТЗ: iPhone подключается к компьютеру, а Windows показывает активный телефон после сопряжения.

```
SwiftUI / AVFoundation → libwebrtc H.264 + audio
                    ↘ локальный WSS signaling ↙
             ICE + DTLS-SRTP напрямую по LAN
                           ↓
             WebRTC в WebView2 → окно видео
                           ↓
             OBS Window Capture → OBS Virtual Camera
                           ↓
                   Discord / Zoom / браузер
```

Safari-клиент использует тот же signaling и WebRTC, оставаясь независимым от сборки IPA. HTTP-страница камеры не обслуживается: HTTP-порт отдаёт только публичный CA, который нужно сверить по SHA-256 до установки. Сигналинг не содержит видео, кодов Apple ID и токенов сторонних служб.

Проекты Windows:

- Core: режимы качества, коды, настройки, интерфейсы сети.
- Transport: HTTPS, WSS, ограничение сообщений и pairing, CA, DNS-SD.
- Video: представление реальных метрик WebRTC. Декодер выполняется внутри браузерного движка.
- VirtualCamera: клиент OBS WebSocket 5 с challenge-response, сцена Window Capture, проверка статуса virtual cam.
- Desktop: WPF, отдельное окно видео с WebView2, трей, снимки/запись, папка, автозапуск по желанию.
- Setup: per-user установщик с встроенным payload и .NET runtime.

## Низкая задержка

WebRTC управляет потерями и очередями. Receiver дополнительно ограничивает bitrate по потерям и RTT; верхний предел на отправителе ограничен выбранным режимом. Экономия энергии iOS снижает режим до 480p и яркость; critical thermal state останавливает трансляцию. Предпросмотр не использует очередь отдельных bitmap в WPF.

## Состояния и безопасность

Соединение: ожидание → ввод кода → подтверждение Windows → paired → peer-ready → offer/answer → connected. Потеря receiver приводит к переподключению receiver. Потеря publisher требует нового кода, потому что постоянная криптографическая идентичность пока не реализована. Нельзя одновременно утверждать наличие доверенных устройств и хранить один IP как доказательство доверия.

Ключ CA находится в папке данных текущего пользователя, не в репозитории или установочном пакете. Защита опирается на права профиля Windows; DPAPI и защищённое хранение на уровне приложения ещё не добавлены. Новый адрес сети требует перезапуска сервера, чтобы попал в SAN сертификата. Лист сервера выдаётся на 30 дней и обновляется при следующем старте.

## Резервные пути

Нет mDNS → ручной IP. Нет native IPA → Safari с доверенным HTTPS. Нет USB Personal Hotspot → Wi-Fi. Нет собственного virtual device → OBS. Нет дискретной GPU → доступный декодер WebRTC. Отсутствие OBS или iPhone не превращает предварительный просмотр в проверенную виртуальную камеру.
